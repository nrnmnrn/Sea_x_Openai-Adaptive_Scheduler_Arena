# 原型工作分類與第一批開發範圍

## 使用方式

本表是使用者核准的原型工作分類，依 [workflow](../../workflow.md) 執行，不核准未決產品答案或整份子 PRD。Owner 開始前在 Ticket 記錄採用列、實際檔案範圍、接口問題、排除部分與未驗證項；不用等待全部 D 項解除。人名、分支和實作能力尚未核實，不由本表虛填。

- **A 可獨立開發**：只用已明確規則及組內資料，不改共享型別或控制行為。
- **B 邊做邊談接口**：先做不依賴待決答案的內部部分；外部連接集中在局部邊界，記明候選方案而非宣告新公開契約。真實呼叫須符合 workflow 試接條件。
- **C 先決定受影響部分**：產品語意、責任、正式狀態修改、安全與錯誤恢復尚未明確，僅這部分等待。不得把 C 改名 B 以自行填值。

以下分類附限制；若實作時發現 A／B 實際依賴未決答案，將該部分轉 C 並記錄，其他部分繼續。A／B 是既有 Ticket 內工作，不新增水平 Ticket 或改變完整交付責任。

下表逐交付列出可做邏輯、排除操作及接口 ID；每個 I 項在討論表對應 H 交接與 D 決策，子 PRD 的正式交付表列驗證與所需上游。Owner 在 Ticket 補實際檔案範圍及未驗證項即可，不在各文件複製另一份分類。正式交付的 D 清單也包含需由上游證明的條件，不代表下游取得該能力的實作責任。

## 第一批執行

1. SP-01 繼續既有工作。SP-02～04 Owner 可選上述 A／B 的明列內部範圍，依 workflow 記錄後開始；C 不被本次流程批准解除。
2. 人類指定整合協調人及各接口討論參與者，在[討論表](interface-discussion-board.md)填人名、最晚需答案時間與既有實作位置。先處理 I03 共用評估、I09 Hybrid 真實來源，以及眼前要執行的控制／隔離問題。
3. 各組產出真實可用版本時即通知整合人；取得必要同意，在隔離環境試接。使用原 SP-01 開發版不等於要求其提前切片／merge。
4. 第一個原型里程碑由人類選定展示情境、範圍與時間；候選是「真實運作→評估既有方法→結果可見」，後續再串候選與啟用。這是建議順序，不變更完整產品要求，也不假定資料必然全敗／通過。
5. 每天短時間只處理即將卡住的表單列；記錄編寫完成、待試接、開發版接通、正式交付各自證據，不以寫完代替跑通。

## 不能省略的交接

提供／使用者、產品含義、版本對應與副作用責任先明確；名稱及資料包裝可局部適配，但不得改變含義或悄悄擴充公開 schema。完整交付仍逐項對照[依賴索引](../../sub-PRDs/DEPENDENCIES.md)、[H1～H8](../contracts/adaptation-contract.md)與原驗收。SP-02 的既有評估故障恢復包含在 S02-A，UI 在 S02-C，不等待 SP-04。
